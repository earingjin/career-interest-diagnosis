# 결과 버전과 추천직업 카탈로그 관리

이 문서는 결과에 남는 버전 값의 의미, 추천직업 카탈로그의 변경 감지·승인 절차를 정리한다.

## 1. 버전 종류

| 이름 | 위치 | DB 저장 | 의미 |
|---|---|---|---|
| `SCORING_VERSION` | `src/lib/scoring/version.ts` | **저장됨** (`results.scoring_version`, 제약 없는 텍스트) | 결과 계산 규칙의 버전. 제출할 때의 값이 결과 행에 남는다. |
| `JOB_CATALOG_VERSION` | `src/content/version.ts` ↔ `src/content/job-catalog.json` 의 `version` | 저장 안 됨 | 추천직업 카탈로그 데이터의 개정 번호. 코드와 JSON 이 같아야 한다(테스트로 확인). |
| 해설·조합 해석 등 | `src/content/version.ts` | 저장 안 됨 | 문안 개정 번호. 각 JSON 의 `version` 과 같아야 한다. |

`SCORING_VERSION` 이라는 이름은 처음 채점만 가리켰으나, 지금은 **점수 계산과 추천직업 선정을 포함한 결과 계산 규칙 전체**의 버전이다.
이름은 DB 컬럼(`scoring_version`)과 맞추기 위해 그대로 둔다.

## 2. SCORING_VERSION 이력

| 버전 | 추천직업 선정 | 점수·1·2순위·동점 처리 |
|---|---|---|
| 1.0.0 | 고령자 목록(seniorJobs) → 일반성인 목록(generalJobs)의 앞쪽 5개 | 기준 |
| **1.1.0** | 퇴직경찰 추천직업 카탈로그의 **승인된 대표 5개를 고정 순서로 우선 추천**, 제외·중복으로 부족할 때만 기존 목록으로 보충 | 1.0.0 과 같다 |

**1.1.0 으로 올린 이유:** 제출된 결과의 추천직업이 어느 규칙으로 만들어졌는지 DB 값만으로 구분하기 위해서다.
채점 계산은 바꾸지 않았다. 과거에 저장된 결과는 `1.0.0` 으로 남고, 저장된 직업명 그대로 표시된다(재계산하지 않는다).

**올려도 안전하다고 확인한 근거** (모든 참조 위치 점검)

- 값을 만드는 곳은 `score.ts`(→ `submit/route.ts` → DB 함수 `submit_session`) 한 곳뿐이다.
- DB 함수는 `p_result->>'scoringVersion'` 을 그대로 저장하고, 컬럼에는 형식·값 제약이 없다.
- 읽는 곳은 `sessionResult.ts` → `view.ts` 의 `scoringVersion` 전달뿐이며, 이 값으로 분기하거나 화면에 표시하는 코드는 없다.
- 테스트의 `"1.0.0"` 리터럴은 "과거에 저장된 결과"를 흉내 낸 데이터라 그대로 두어야 한다(과거 결과 호환성 확인용).

**언제 올리는가:** 점수 계산, 1·2순위·동점 처리, 추천직업 선정 규칙(대표 고정·보충·폴백 순서·중복 처리 등)이 바뀔 때.
카탈로그의 데이터(어떤 직업이 대표인지 등)만 바뀔 때는 `SCORING_VERSION` 이 아니라 카탈로그 버전을 올린다.

> 한계: 결과 행에는 카탈로그 버전이 남지 않는다. 같은 `1.1.0` 안에서 카탈로그 데이터가 개정되면 결과 행만으로는 어느 개정판인지 알 수 없다.
> 구분이 필요하면 제출 시각(`sessions.submitted_at`)과 배포 날짜를 대조한다. DB 변경은 별도 승인이 필요하다.

## 3. 카탈로그 변경 감지

`src/content/__tests__/job-catalog-lock.test.ts` 는 카탈로그 전체의 표준 해시(키 순서·들여쓰기 무관, 배열 순서 유지)를 버전별로 기록한다.
**카탈로그가 바뀌면 이 테스트가 실패한다.**

카탈로그를 고쳤다면(대표·보충 후보·승인 상태·표시명·문구 무엇이든):

1. `job-catalog.json` 의 `version` 과 `src/content/version.ts` 의 `JOB_CATALOG_VERSION` 을 같은 새 버전으로 올린다.
2. 테스트 파일의 `LOCK` 에 `"새 버전": "새 해시"` 를 **추가**한다. 해시는 실패 메시지에 나온다. 이전 버전의 줄은 고치지 않는다.
3. `node scripts/verify-job-catalog.mjs`(원본 PDF 대조, 로컬)와 `npm test` 를 다시 실행한다.

아직 배포·커밋 전인 버전(현재 `0.2.0`)은 같은 버전 안에서 해시만 갱신해도 된다.
대표 30개의 ID·이름·순서는 `jobCatalog.test.ts` 에도 고정되어 있어, 해시만 바꿔서는 통과하지 않는다.

## 4. 추천 정책

- **대표 5개(유형별)** 는 승인된 순서대로 고정 우선 추천한다. 무작위·시간·세션 값은 쓰지 않는다.
- 대표가 보류·비활성이거나 다른 유형(1순위)과 중복되면 그 자리만 비우고 다음 순서로 채운다.
- **추천에 쓰는 카탈로그 항목은 `displayReview = approved` 뿐이다.**
  - `provisional`(승인 대기): 개별 검토는 마쳤지만 담당자 승인 전이므로 **추천에 쓰지 않는다**. 승인하면 `approved` 로 바꾸고 3절 절차를 따른다.
  - `needs-review`(검토 보류): 쓰지 않는다. 사유는 `reviewCodes`.
- 대표가 부족하면 승인된 보충 후보(현재 없음), 그다음 기존 목록(seniorJobs → generalJobs)으로 채운다. 기존 목록도 부족하면 채운 만큼만 보여 주고 `count` 로 드러낸다.
- 이름 끝 글자 같은 규칙은 추천 가능 여부를 정하지 않는다. `displayReview` 로만 정한다.

## 5. 표현 정책

직업명·자격·선발 조건은 **검증되지 않았다**(`verification.name = unverified`, `needsCheck.confirmed = false`).
카탈로그 대표든 기존 목록 폴백이든 화면에서 자격·채용 가능성이 확인된 것처럼 쓰지 않는다.
화면에는 "직업흥미와 추천직업은 능력·자격이나 취업 가능성을 확정하지 않습니다.", "관심 있는 직업의 실제 업무와 채용요건은 별도로 확인하세요." 안내가 항상 있다.
`recommendationWording.test.tsx` 가 30개 조합 × (대표 / 폴백 일부 / 폴백만) 의 고객·A4 화면에서 보증 표현이 없고 안내가 있는지 확인한다.
