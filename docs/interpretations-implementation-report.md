## 기준과 작업 범위

- 사용자 확인을 받은 `main` / `59e1d019aa04acec14a2e644d25f0c48a218e233`를 기준으로 작업했다. 시작 시 작업 트리는 깨끗했으며 브랜치 변경·원격 병합·커밋·푸시·배포를 수행하지 않았다.
- 해설 콘텐츠, 결과 뷰 모델, 공통 결과 표시, 인쇄 여백과 관련 검증만 수정했다.
- 고객 출력 제한과 FR-01~FR-03 및 FR-05~FR-06 베타 UX는 유지했다.
- 별도의 공식 원본 문서는 로컬에서 찾지 못했다. 확인 가능한 기준 커밋의 `interpretations.json`과 `content/CORRECTIONS.md`를 참고했고, 공식 원문을 직접 확인하거나 인용했다고 주장하지 않는다.

## 최종 문안

[6개 유형의 최종 문안 전문](interpretations-final-copy.md)에 유형별 4개 영역의 문구를 모두 수록했다. 실행 데이터는 `src/content/interpretations.json` 한 곳에서 관리한다.

4개 영역은 `나의 직업흥미 특성`, `선호하는 활동과 업무 환경`, `중장년 전직·재취업 탐색`, `추천직업과 확인사항`이다. 유형별 서술 필드는 9개이며 본문 분량은 285~308자로 균형을 맞췄다(키워드·공통 안내 제외).

- 전직 탐색 영역에는 **“흥미유형에 기초한 일반 안내이며, 검사에서 직접 측정한 결과가 아닙니다.”**를 두 순위 모두에 표시한다.
- 추천직업 영역에는 **“취업 가능성이나 직무 적합성을 확정한 목록은 아닙니다.”**를 표시한다.
- 흥미와 능력·자격·취업 가능성을 구분하고, 경찰 경력에 한정하지 않는 경험 활용·교육·체력·근무조건 안내를 작성했다.
- 추천직업은 저장된 단일 목록을 사용하며 고령자/일반성인 구분을 화면에 노출하지 않는다.

## 유지한 원칙과 데이터 호환성

- 일반성향 42문항·형용사 30개·최소 5개 선택·합산 방식·상위 두 유형·RIASEC 순서 동점 처리·제출 시 저장을 유지했다.
- **`SCORING_VERSION=1.0.0` 유지.** 문항 JSON의 버전과 내용도 변경하지 않았다. 기존처럼 문항·해설 버전을 한 값에 맞추면 문항까지 개정한 것으로 보일 수 있어 해설 버전만 분리했다.
- `selectJobs()`의 고령자 우선, 부족할 때 일반성인 보충, 유형당 최대 5개, 기존 배열 순서, 동일 유형/두 순위 전체의 중복 제거, trim·빈 문자열 제외, 가능한 수만 반환하는 동작은 그대로다.
- 기준 커밋과 R/I/A/S/E/C 각각의 `seniorJobs`/`generalJobs` **12개 배열이 이름과 순서까지 완전히 같음**을 확인했다. 배열 직렬화 SHA-256은 `2f147692ce99b7d2d1ab7e1d69ee280987ec2ff602c9901f8739d85680360abe`로 고정 검증한다.
- DB 스키마·세션 인증·관리자 인증·제출 API·저장 구조를 변경하지 않았다. 새 API·테이블·라이브러리를 추가하지 않았다.
- 기존 완료 기록은 업데이트하지 않는다. 조회 시 새 해설 문안으로 표시하지만, 과거에 저장된 점수·순위·추천직업·채점 버전은 그대로 사용한다. 해설이 DB에 과거 버전별로 저장되는 구조는 아니므로 문안의 시점별 보존이 필요하면 별도 정책이 필요하다.
- 실제 DB 검증은 무작위 테스트 과정/고객만 생성하고 해당 데이터만 정리했다. 기존 완료 테스트나 운영 결과의 일괄 수정은 수행하지 않았다.

## 제출 전 해설 노출 방지

1. 런타임 JSON import는 `interpretations.server.ts` 한 곳에만 있으며 `server-only`를 선언했다. 채점과 결과 로더가 이 경계를 사용한다.
2. 클라이언트 컴포넌트는 전체 해설 JSON을 import하지 않는다. 결과 타입은 `import type`으로 사용한다.
3. 기존 `loadResult()`의 쿠키/과정/제출 상태 확인 및 `loadSessionResult()`의 제출 상태·결과 무결성 검증을 유지했다.
4. 결과 뷰에는 해당 고객의 1·2순위 해설만 들어간다. 6유형 점수표의 유형 이름은 유지되지만 다른 네 유형의 해설 원문·전체 직업 배열은 전달하지 않는다.
5. 프로덕션 클라이언트 JavaScript **14개 파일**을 Unicode escape도 해석해 검사했고, 6유형의 해설 원문이 검출되지 않았다. 최종 빌드 후에도 재검사했다.
6. 실제 브라우저로 진단 HTML/RSC와 제출 전 결과 URL 응답에서 6유형 해설 비노출을 확인했다. 제출 후 응답에서는 상위 두 유형의 모든 서술 필드가 있고 다른 유형 원문은 없음을 확인했다.
7. 관리자 결과 상세는 기존 인증 없이 열 수 없으며 고객 쿠키로도 접근하지 못한다. 결과 조회용 공개 API를 만들지 않았다.

정상 제출 후 화면에 표시되는 1·2순위 해설은 개발자도구로 읽을 수 있다. 이를 숨기거나 브라우저 자체 인쇄·캡처를 막는다고 주장하지 않는다.

## 고객·관리자 문안 동일성과 A4

- 같은 세션에 대해 `loadResult()`와 `loadAdminResultDetail()`이 생성한 뷰 전체가 동일함을 자동 테스트로 확인했다. 두 화면은 동일한 `GroupList`/`JobList`를 사용한다.
- 실제 DB·서버 검증에서는 상위 두 유형의 해설·추천직업·공통 안내 문구가 고객 웹 결과와 관리자 출력에 모두 있는지 확인했다. 고객 쪽에는 A4 마크업/출력 버튼이 없고 관리자에게만 출력 기능이 있다.
- 첫 A4 검증은 새 문안 길이 때문에 **실패**했다. 여백과 배치를 조정했으며 문구를 삭제·축약하지 않았고 본문 글자를 줄이지 않았다.
- 최종 인쇄: 기존 210×296mm 한 장, 본문 **10pt**, 기존 줄간격·그래프 크기 유지. 상하 5mm·좌우 10mm 여백, 항목명/설명 이어 배치, 행·구획 여백 정리.
- 최종 검증은 **30가지 1·2순위 조합 모두 PDF 한 장, 겹침·잘림 없음**. 본문~점수표 사이 최소 약 **14.8px**. 검증기의 안전 여백 기준도 8px 이상으로 강화했다.
- 관리자 A4 미리보기·목록 복귀·인쇄 버튼·인쇄 시 도구줄 숨김을 유지했다.

### 중간 실패와 처리

- 초기 A4 검증에서 30조합의 본문/점수표 겹침을 검출했다. 문구·10pt를 유지하고 인쇄 배치와 여백을 조정한 뒤 30조합을 재검증했다. 단순히 PDF가 한 장이라는 이유만으로 통과 처리하지 않았다.
- 한 차례 모바일 실행은 실행 중인 프로덕션 서버의 빌드 자산이 교체된 상태에서 진행되어 진단 로딩 대기 타임아웃이 발생했다. 검증용 서버를 종료하고 새 빌드 서버에서 재실행해 37개 모두 통과했으며 실패 실행의 임시 데이터도 정리했다.
- 서버에서 스트리밍 prerender 완료 후 fetch 취소 로그가 일부 관찰됐다. 기존 서버 조회/예외 처리 경로는 변경하지 않았고 최종 브라우저 JavaScript 예외 검증은 통과했다. 이 로그의 기존/신규 여부에 대한 수정 전 비교 검증은 수행하지 않았다.

## 미검증·잔여 위험

- 실제 iOS/Android 스마트폰, 운영체제 인쇄 대화상자·실물 프린터는 미검증이다. Chromium 모바일 에뮬레이션과 Chrome PDF 생성/레이아웃 측정 결과를 실기기 검수 통과로 대신 보고하지 않는다.
- A4는 현재 문안·현재 추천직업 데이터의 30조합을 검증했다. 문안을 늘리거나 직업명을 바꾸면 출력 검증을 다시 해야 한다. 5mm 상하 여백은 실제 프린터에서 확인이 필요하다.
- 별도 공식 원본을 받으면 개념 대조·표현 검토를 추가할 수 있다. 새 탐색 안내는 해당 검사의 측정 타당도나 취업 가능성의 보장을 의미하지 않는다.
- 과거 결과를 조회하면 최신 해설을 표시한다. 과거 시점의 해설을 재현해야 하는 요구가 생기면 콘텐츠 버전 보존 정책을 먼저 결정해야 한다.
- 고객 출력 제한은 서비스 제공 기능에 적용된다. 화면에 정상 표시된 결과의 브라우저 자체 인쇄·스크린샷까지 막지 않는다.
- 커밋·푸시·배포는 수행하지 않았다.
